UseArazzo Runner

Executes Arazzo workflows step by step against live APIs, and hands back a full run trace, not just a pass or fail.

An Arazzo document describes a sequence of API calls. @usearazzo/runner makes those calls. It sends real requests to the APIs behind the workflow's OpenAPI source descriptions, checks each step's success criteria, follows the control flow the document declares, and tells you what happened at every step.

Read the API reference View source on GitHub

Supported versions:

  • ✓ Arazzo 1.0.0, 1.0.1, 1.1.0 (workflow documents)
  • ✓ OpenAPI 2.0, 3.0.x, 3.1.x (source descriptions)

Run a Workflow

Today the Runner is a library: ArazzoRunner loads a document and runs a workflow in two calls. Here it runs a Petstore workflow that logs in, finds a pet, orders it, and checks the order. Start a local Petstore for it to call first:

docker run --rm -p 8080:8080 swaggerapi/petstore3:1.0.28

Install the Runner in an empty directory:

npm install @usearazzo/runner

Save this script there as run.mjs and run it with node run.mjs:

import { ArazzoRunner } from '@usearazzo/runner';

const runner = await ArazzoRunner.load(
  'https://usearazzo.com/assets/reference/runner/petstore-order.arazzo.yaml',
);

const result = await runner.execute('authenticateAndOrderPet', {
  inputs: {
    username: 'theUser',
    password: '12345',
    preferredPetStatus: 'available',
    orderQuantity: 1,
  },
  executeOptions: {
    petstoreAPI: { server: 'http://localhost:8080/api/v3' }, // a local Petstore
  },
});

for (const step of result.steps) {
  const mark = step.successful ? '✓' : '✗';
  const time = `${Math.round(step.durationMs)} ms`;
  console.log(`${mark} ${step.stepId.padEnd(26)}${time.padStart(7)}`);
}
console.log(`\n${result.status} in ${Math.round(result.durationMs)} ms`);
node run.mjs 
$ node run.mjs
✓ loginUser                  739 ms
✓ findAvailablePets           19 ms
✓ placeOrder                  17 ms
✓ retrieveOrderedPetDetails    9 ms
✓ verifyOrderConfirmation      7 ms

completed in 796 ms

Five real requests, each judged by its step's criteria. The result also carries the workflow's outputs, and for each step the action it picked and how many attempts it took. The API reference walks through the same run, outputs included.

What It Handles

The control flow you wrote

goto, retry with retryLimit and retryAfter, and end, as the specification defines them. Workflow-level default actions and parameters reach every step. A runaway loop stops at a step budget.

Workflows that call workflows

Sub-workflow steps, dependsOn prerequisites, and one-way transfers with goto, including workflows in other Arazzo documents. Cycles are caught, and a dependency runs once per run.

Your HTTP stack, your credentials

Requests go out through global fetch by default, or through any client you plug in. Arazzo itself is auth-agnostic, so credentials come from you.

A trace, not a verdict

Every step in run order: whether it passed, which action was picked, how many attempts it took, and how long it ran. A failed step is a result you read, not an exception you catch.

Authentication

Arazzo says nothing about credentials, so they come from you. There are three places to put them. Start with the first, and fall back to the next when it cannot express what you need.

1. Execute options: static credentials per API

Each entry of executeOptions is named after a source description of your workflow document and reaches only the steps that call that API. Its securities name the security schemes the API's OpenAPI document declares:

const result = await runner.execute('buyPet', {
  inputs,
  executeOptions: {
    petstoreAPI: {
      securities: { authorized: { api_key: 'KEY' } },
    },
    paymentsAPI: {
      securities: { authorized: { bearerAuth: 'TOKEN' } },
    },
  },
});

Each credential goes where its scheme says (header, query, or cookie), and only to the operations that require it. API keys, bearer tokens, basic auth, and OAuth tokens are covered. The key for one API is never sent to another, even when both name a scheme alike.

2. Request interceptor: credentials computed per request

A token you fetch or refresh, a signed request, or an API whose OpenAPI document declares no security scheme: none of these fit a static entry. A requestInterceptor runs after each request is built and before it is sent, and changes it as you see fit:

const runner = await ArazzoRunner.load(uri, {
  requestInterceptor: async (request) => {
    request.headers.Authorization = `Bearer ${await acquireToken()}`;
  },
});

Credentials from the execute options are already on the request when the interceptor sees it, so the two combine. An interceptor can also sit inside one API's entry of executeOptions, where it touches only that API's requests.

3. Custom HTTP client: credentials in the connection

Some credentials never appear in a request at all. A client certificate (mutual TLS) or an authenticating proxy belongs to the connection, so it belongs to the httpClient, the function that sends every request:

import { fetch, Agent } from 'undici';

const dispatcher = new Agent({ connect: { cert, key, ca } });

const runner = await ArazzoRunner.load(uri, {
  httpClient: (request) => fetch(request.url, { ...request, dispatcher }),
});

Keep changes to the request itself in the interceptor. What a client changes on its own does not show up in the trace.

All three are about API calls. Loading documents is a separate path: workflow and OpenAPI documents behind a token or a client certificate load through the reference option, and credentials for an API never reach a host that only serves a document.

The Runner runs no OAuth flow: you supply the tokens. Every credential form is in the API reference, and document retrieval has its own section.

Architecture

Running a workflow is a pipeline of four small parts, and ArazzoRunner wires them for you. WorkflowExecutor runs the steps and is the only part that writes run state. StepExecutor runs one step. OpenAPIOperationExecutor builds and sends one request. DocumentRegistry loads every document once. Each part takes its collaborator rather than building one, so you can swap any of them, or drop in a stub for tests.

HTTPClient is drawn dashed because it is the seam you are meant to replace. The API reference documents each part.
